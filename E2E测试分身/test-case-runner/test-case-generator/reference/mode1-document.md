# 模式一: 需求文档 → 浏览器预探索 → 测试用例

> 本文档为 `test-case-generator` skill 的模式一详细规则,只描述模式一独有的内容。共用部分见: [SKILL.md](../SKILL.md)(整体流程与基础探索) | [ai-benchmark-syntax.md](./ai-benchmark-syntax.md)(AI 验证基准语法) | [page-structure-yaml-spec.md](./page-structure-yaml-spec.md)(yaml 规范)

---

## 1. 模式说明与输入特征

- **输入**: 需求文档(`design.md`/`proposal.md` 等及其关联文档),通过两个子模式之一获取
- **功能点来源**: 文档原文(proposal 目标 + design 页面/交互 + specs 行为 + tasks 测试要求)
- **浏览器探索角色**: **辅助性**预探索(仅 navigate+snapshot,不深度交互),用于校准文档中提到的元素名
- **失败后果**: 可降级,用例保留 `<>` 占位符仍能生成

模式一**不要求用户直接提供 `design.md`/`proposal.md` 路径**,而是由 skill 通过子模式 1A 或 1B 主动获取文档。

> 浏览器预探索的完整流程见 [SKILL.md](../SKILL.md) 第二步。模式一在提取功能点前需先完成第 2 节子模式判定与文档获取。

## 2. 子模式判定与文档获取

### 2.1 子模式判定规则

进入模式一后,按以下优先级判定子模式(用户显式指定 > 输入特征自动判定 > 默认子模式 1B):

| 优先级 | 判定条件 | 子模式 | 说明 |
|--------|---------|--------|------|
| 1 | 用户显式指定(如"用 1A""我提供文档""按这份 design 生成""用 1B""从 openspec 找""自动发现 change") | 对应子模式 | 用户意图明确,直接采用 |
| 2 | 用户在对话中提供了文档(路径 / 粘贴内容 / 文件引用),或包含"这份文档""这个 design""按这个 proposal""这份需求"等关键词 | **1A 用户提供文档** | 用户直接提供文档 → 获取关联文档 → 功能点(详见 2.2) |
| 3 | 用户未提供文档,且包含"openspec""change""apply 完成""当前 change""自动发现""从 change 找"等关键词 | **1B openspec 自动发现** | 扫描 openspec → 选择 apply 完成的 change → 功能点(详见 2.3) |
| 4 | 用户未提供文档且未明确指定 | **1B openspec 自动发现**(默认) | 默认尝试自动发现 apply 完成的 change;若无符合条件的 change 则回退询问用户 |

> **判定要点**:
> - **优先级 1 最高**:用户显式指定时直接采用,不进行后续判定
> - **优先级 2-3 按顺序匹配**:首个命中的子模式即采用,不继续判定
> - **默认倾向**:用户未明确提供文档且未指定子模式时,默认采用 1B(自动发现 openspec change),因为模式一主要服务于已完成 apply 的 change 的测试用例生成
> - **混合输入处理**:若用户既提供了文档又提到 openspec change,优先采用 1A(用户提供的文档优先级更高)

### 2.2 子模式 1A: 用户提供文档

#### 2.2.1 用户文档识别

按以下顺序识别用户提供的文档:

| 用户提供形式 | 识别方式 | 处理 |
|-------------|---------|------|
| 绝对/相对文件路径(以 `.md` 结尾或包含路径分隔符) | 正则匹配路径模式 | 用 `Read` 工具读取文件内容,记录路径用于关联文档获取 |
| 粘贴的 Markdown 内容(含 `#` 标题、`\|` 表格等) | 内容特征识别 | 直接使用粘贴内容,询问用户是否需要关联其他文档 |
| 文档名引用(如"design.md""proposal") | 关键词匹配 `design`/`proposal`/`tasks`/`specs` | 在 `openspec/changes/` 下搜索同名文件,找到后读取 |
| Change 名称引用(如"tsg-ai-portal 的设计文档") | 匹配 `openspec/changes/<name>/` 目录 | 进入 2.2.2 场景 D 获取该 change 的全部关联文档 |

#### 2.2.2 关联文档自动获取

识别用户提供的文档后,根据文档所在位置自动获取关联文档:

**场景 A: 文档位于 openspec change 目录内**(如 `openspec/changes/<change-name>/design.md`)

自动获取同目录下的关联文档:

| 用户提供的文档 | 自动获取的关联文档 | 用途 |
|---------------|------------------|------|
| `proposal.md` | `design.md`、`tasks.md`、`specs/*/spec.md`、`contracts.md`(若存在) | 从目标→设计→任务→规格全链路提取功能点 |
| `design.md` | `proposal.md`、`tasks.md`、`specs/*/spec.md`、`contracts.md`(若存在) | 设计文档为主,回溯目标,下探任务和规格 |
| `tasks.md` | `proposal.md`、`design.md`、`specs/*/spec.md` | 任务清单为主,回溯设计和目标 |
| `specs/<spec-name>/spec.md` | `proposal.md`、`design.md`、`tasks.md` | 规格为主,回溯设计上下文 |
| `contracts.md` | `proposal.md`、`design.md`、`tasks.md` | 契约为主,回溯设计上下文 |

**场景 B: 文档位于 openspec change 归档目录内**(如 `openspec/changes/archive/<change-name>/design.md`)

同场景 A,从归档目录获取关联文档。归档 change 的文档同样有效。

**场景 C: 文档为独立文件**(如用户粘贴的纯文档内容、非 openspec 目录的文件)

- 询问用户是否还有关联文档可提供(如"是否还有 design.md / tasks.md / specs 等文档?")
- 若用户提供,继续读取;若无,仅使用已提供的文档提取功能点
- 在 `.md` 顶部标注 `> ⚠️ 文档来源: 仅用户提供,未获取到关联文档,功能点覆盖度可能受限`

**场景 D: change 名称引用**(如"tsg-ai-portal 的设计文档")

- 定位到 `openspec/changes/<change-name>/` 目录
- 按"用户未指定具体文档"处理,获取全部关联文档: `proposal.md` + `design.md` + `tasks.md` + `specs/*/spec.md` + `contracts.md`
- 这种场景下功能点覆盖最全

#### 2.2.3 文档读取规则

- 使用 `Read` 工具读取关联文档,每篇文档完整读取(不限制行数,除非文件过大)
- 文档过大时(>1000 行),先读目录/章节标题,再按需读取相关章节
- 读取失败(文件不存在 / 权限不足)时跳过该文档,并在最终输出的"文档来源"中注明缺失
- 读取顺序建议: `proposal.md` → `design.md` → `specs/*/spec.md` → `tasks.md` → `contracts.md`(从目标到实现,建立上下文)

### 2.3 子模式 1B: openspec 自动发现

#### 2.3.1 扫描 openspec changes 目录

扫描以下两个目录,发现所有 change:

| 扫描目录 | 说明 | change 状态 |
|---------|------|------------|
| `openspec/changes/` | 活跃 change(尚未归档) | 进行中 |
| `openspec/changes/archive/` | 已归档 change | 已完成并归档 |

对每个发现的 change 目录,读取其 `.openspec.yaml` 元数据(若存在)和 `tasks.md`。

#### 2.3.2 apply 完成度检测

检测 change 是否已完成 apply 环节,判定规则(按优先级,首个命中即采用):

| 优先级 | 判定条件 | 说明 |
|--------|---------|------|
| 1 | `.openspec.yaml` 中有明确的 `stage` 或 `status` 字段且值为 `applied`/`implemented`/`done` | 元数据显式声明 |
| 2 | `tasks.md` 末尾存在"Design Trace 覆盖核对"表,且所有 Trace 的状态列均为 `✅` | 任务完成度 100%(如 `| D-DB-001 | T-DB-001 | ✅ |`) |
| 3 | `tasks.md` 中所有实现类任务(`Action: add`/`update`/`fix`)均标注完成(如含 `✅`/`[x]`/`已完成`) | 任务级完成标记 |
| 4 | change 目录位于 `openspec/changes/archive/` 下 | 归档目录的 change 视为已完成 apply |
| 5 | 以上均无法判定 | 视为未完成,排除出候选列表 |

> **说明**: 优先级 4(归档目录)是强信号——归档意味着 change 已走完 verify → archive 流程,apply 必然完成。优先级 2-3 通过 tasks.md 的完成标记判定,适用于活跃 change。

#### 2.3.3 候选 change 选择

扫描完成后,汇总所有"apply 已完成"的 change 候选:

- **候选数为 0**: 报错,提示用户"未发现已完成 apply 环节的 openspec change,请确认 change 状态或改用子模式 1A 直接提供文档"
- **候选数为 1**: 直接采用该 change,向用户报告"已发现 apply 完成的 change: `<change-name>`,将基于其文档生成测试用例"
- **候选数为多个**: 用 `AskUserQuestion` 询问用户选择哪个 change,选项格式:
  - label: `<change-name>`(简短)
  - description: `apply 完成时间/来源(活跃或归档)/功能简述`(若能从 proposal 提取)
  - 最多展示 4 个选项,超出时提示用户输入 change 名称

#### 2.3.4 change 文档获取

用户选择 change 后(或候选数=1 自动采用),获取该 change 的全部关联文档:

| 文档 | 路径 | 用途 |
|------|------|------|
| `proposal.md` | `openspec/changes/[archive/]<change-name>/proposal.md` | 业务目标级功能点 |
| `design.md` | `openspec/changes/[archive/]<change-name>/design.md` | 页面与交互级功能点(主要来源) |
| `tasks.md` | `openspec/changes/[archive/]<change-name>/tasks.md` | 测试任务级补充功能点 |
| `specs/*/spec.md` | `openspec/changes/[archive/]<change-name>/specs/<spec-name>/spec.md` | 行为要求级功能点 |
| `contracts.md` | `openspec/changes/[archive/]<change-name>/contracts.md`(若存在) | 接口契约级补充 |

读取规则同 2.2.3。读取失败时跳过缺失文档,在"文档来源"中注明。

### 2.4 URL 获取

两个子模式均需要目标 URL 进行浏览器预探索,获取方式:

1. **优先从文档中提取**: 读取 `design.md` / `proposal.md` 时,搜索其中是否提到页面 URL、路由路径、前端页面地址等
2. **询问用户**: 若文档中未明确 URL,通过对话询问用户:"请提供需要探索的页面 URL(用于校准 UI 元素名)"
3. **用户可拒绝**: 若用户表示无 URL 或暂不探索,降级为无探索模式(见 [SKILL.md](../SKILL.md) 2.4 节)

### 2.5 子模式记录

在最终输出的 `.md` 顶部和 `.page-structure.yaml` 中记录所采用的子模式:

- `.md` 头部: `> **子模式**: <1A 用户提供文档 / 1B openspec自动发现>`、`> **来源 change**: <change 名称或"用户提供的文档">`
- `.page-structure.yaml`: `source_type: document`、`source_change: <change-name 或 null>`、`submode: 1A | 1B`

## 3. 功能点提取

### 3.1 功能点提取来源

从获取的文档中按以下优先级提取功能点:

| 来源文档 | 提取的功能点类型 | 提取规则 |
|---------|----------------|---------|
| `proposal.md` | **业务目标级**功能点 | 从"目标""Goals""为何要做"等章节提取业务目标,每个目标对应一个功能点 |
| `design.md` | **页面与交互级**功能点(主要来源) | 从"页面设计""交互流程""UI 设计""Implementation Trace"等章节提取:每个页面、每个交互操作、每个表单、每个对话框均为一个功能点 |
| `specs/<spec-name>/spec.md` | **行为要求级**功能点 | 从"Behavior""Requirements""Scenarios"等章节提取:每个行为要求、每个场景为一个功能点 |
| `tasks.md` | **测试任务级**补充功能点 | 从 `Action: test` 的任务中提取测试覆盖要求,作为功能点补充;从 `T-VERIFY` / `T-E2E` 类任务中提取人工验证清单 |
| `contracts.md` | **接口契约级**补充 | 从 API 契约中提取前端调用的接口对应的页面功能(如"查询智能体列表"接口对应"列表展示"功能点) |

### 3.2 功能点提取规则

1. **逐文档提取**: 按上述优先级逐文档读取,提取显式功能点
2. **去重与合并**: 不同文档中描述同一功能的功能点合并(如 proposal 的"创建智能体"与 design 的"新建智能体表单"合并为一个功能点)
3. **保留来源**: 每个功能点记录来源(文档名 + 章节号),填入功能点清单的"来源"列
4. **不臆造**: 文档中未明确提及的功能不提取,即使"看起来应该有"
5. **覆盖度记录**: 提取完成后,统计功能点总数,与文档中的显式功能描述对比,确保无遗漏

### 3.3 功能点 → 场景矩阵

对每个功能点,按以下维度展开为测试场景矩阵:

| 场景类型 | 说明 | 等级 | 必须生成 |
|---------|------|------|---------|
| 正常路径 | 主流程成功场景 | p0 | 是 |
| 必填校验 | 必填字段为空 | p1 | 是(若有必填字段) |
| 边界值 | 长度/数值边界 | p1 | 是(若有边界约束) |
| 枚举切换 | 枚举字段各选项切换 | p1 | 是(若有枚举字段) |
| 异常路径 | 业务异常(如重复、冲突) | p1 | 是(若文档提及异常场景) |
| 权限/状态 | 权限不足、状态不允许 | p1 | 是(若文档提及权限/状态约束) |

> **场景展开依据**: 所有场景必须来自文档原文(如 design 写"名称必填,长度1-50"→ 生成"名称为空"和"名称超长"场景)。文档未提及的异常场景不臆造。

## 4. 功能点清单与页面结构

> `features[]` 为功能点清单(与 `.md` 一致),`cases` 为按用例 ID 索引的执行数据(runner 主入口)。字段规范详见 [page-structure-yaml-spec.md](./page-structure-yaml-spec.md)。

```yaml
module: 智能体管理
source_type: document
submode: 1B  # 1A 用户提供文档 / 1B openspec自动发现
source_change: tsg-ai-portal  # 若来自 openspec change,填 change 名;独立文档填 null
url: https://example.com/agent  # 预探索后填入实际URL
generated_at: 2026-07-07T10:00:00+08:00
features:
  - id: FP-001
    name: 创建智能体
    source: design.md#3.2
    cases: [TC-AGT-001, TC-AGT-002, TC-AGT-003, TC-AGT-004]
    route: /agent/list
  - id: FP-002
    name: 智能体列表展示
    source: design.md#3.3
    cases: [TC-AGT-005]
    route: /agent/list
```

## 5. AI 验证基准生成(模式一场景映射表)

> 共用语法规则(检查项结构、类型判定、语义匹配、.md ↔ yaml 映射)见 [ai-benchmark-syntax.md](./ai-benchmark-syntax.md)。本节仅列出模式一的"文档信息→基准映射"和生成规则。

模式一的 AI验证基准基于**文档中描述的预期行为**编写,预探索获取的真实元素名用于填充占位符。两个子模式的基准生成规则完全一致,仅"关联需求点"格式不同(见 [SKILL.md](../SKILL.md) 4.4 节)。

### 5.1 文档信息→基准映射

| 文档信息来源 | 文档中的内容 | AI验证基准中的应用 |
|------------|------------|-------------------|
| `design.md` 交互流程 | 表单字段、按钮、对话框标题、操作步骤 | 直接引用**文档中的元素名**作为锚点(如对话框标题、按钮文字、表头字段) |
| `specs/*/spec.md` 行为要求 | "应当""必须""禁止"等行为约束 | 转为可观测断言(如"必须校验名称必填" → `出现含"必填"/"不能为空"的校验提示`) |
| `tasks.md` 测试任务 | `Action: test` 任务的覆盖要求 | 补充测试场景的验证点(如"覆盖空值校验" → 补充空值用例的 AI 基准) |
| `contracts.md` 接口契约 | 接口出入参字段、状态码 | 用于量化验证(如"列表返回 N 条" → `底部"共N条"中N值≥1`) |
| 预探索结果(若成功) | 真实页面元素文本、结构 | 替换文档中的 `<>` 占位符为真实元素名 |

### 5.2 生成规则

1. 优先使用**文档中明确写出的元素名**(如 design 写"新建智能体"按钮,基准中用 `"新建智能体"`)
2. 预探索成功后,若文档元素名与真实页面元素名不一致,以**真实页面元素名**为准(如文档写"新建"但页面是"新建智能体",基准用 `"新建智能体"`)
3. 预探索降级时,保留文档元素名并标注 `<>` 占位符(如 `snapshot中不再出现"<对话框标题>"对话框`),在 `.md` 顶部标注"待页面探索确认"
4. 套用对应场景的编写模板,将模板中的占位符替换为文档/探索观察到的真实文本
5. 正常路径:必须包含正向断言(出现什么)+反向断言(不再出现什么)+量化变化(数量增减)
6. 校验场景:使用 `含"A"/"B"` 格式列出文档中提到的**校验提示文本**,同时保留近义词汇兜底
7. 跳转场景:必须描述 URL 变化(包含真实路径关键词)和**至少2个**目标页面特征元素
8. 列表展示场景:必须列出文档中提到的**表头字段名**(至少4个),不用模糊描述
9. 每条基准以 `【步骤N后】` 开头,多个验证点用 `;` 分隔,推荐用 `①②③④` 编号

### 5.3 场景→基准映射表

| 场景类型 | AI验证基准模板 |
|---------|--------------|
| 创建/提交成功 | `【步骤N后】①snapshot中不再出现"<对话框标题>"对话框;②<列表区域>出现含"<操作内容>"的新增记录;③底部"共N条"中N值比操作前增加1;④可能出现含"成功"的提示信息` |
| 必填校验 | `【步骤N后】①snapshot中仍存在"<对话框标题>"对话框(未关闭);②对话框内出现含"必填"/"不能为空"/"请输入"的校验提示;③<列表区域>行数与操作前一致(未增加)` |
| 边界值校验 | `【步骤N后】①snapshot中仍存在"<对话框标题>"对话框(未关闭);②对话框内出现含"长度"/"不能超过"/"超出"的校验提示;③<列表区域>行数与操作前一致(未增加)` |
| 枚举切换 | `【步骤<N-1>后】①snapshot中<选择器>文本变为"<选项名>";②页面不出现error提示;【步骤N后】③snapshot中不再出现"<对话框标题>"对话框;④<列表区域>出现含"<操作内容>"的新增行;⑤可能出现含"成功"的提示` |
| 列表展示 | `【步骤N后】①snapshot中<列表区域>刷新;②表头包含"<字段1>""<字段2>""<字段3>""<字段4>";③底部"共N条"中N值≥1;④页面不出现error提示` |
| 跳转 | `【步骤N后】①snapshot中URL从<源路径>变为<目标路径>;②页面出现"<特征元素1>""<特征元素2>";③页面不再出现<源页面特征>;④页面不出现error提示` |
| 删除成功 | `【步骤N后】①snapshot中不再包含被删除的记录;②底部"共N条"中N值比操作前减少1;③可能出现含"成功"/"删除成功"的提示` |
| 取消/关闭 | `【步骤N后】①snapshot中不再出现"<对话框标题>"对话框;②<目标区域>内容与操作前一致;③列表行数无变化` |

## 6. 输出特点

模式一**以文档为功能点主要来源,浏览器预探索为辅**,因此:
- "点击步骤"列基于文档中的交互描述填写,结合预探索获取的真实元素名补全(如"点击'新建智能体'按钮")
- "AI验证基准"列基于文档中的预期行为编写 + 预探索真实元素名填充,转为 snapshot 可观测描述
- "关联需求点"列按子模式填写(见 [SKILL.md](../SKILL.md) 4.4 节)
- 用例覆盖文档中所有显式功能点(proposal 目标 + design 页面/交互 + specs 行为 + tasks 测试要求)
- `.page-structure.yaml` 中 `source_type: document`,`submode` 填 `1A` 或 `1B`,`source_change` 填 change 名(若来自 openspec)或 `null`(独立文档)
- 若预探索降级,用例中保留 `<>` 占位符并在 `.md` 顶部标注降级原因
- `.md` 末尾的"文档来源"列出所有引用的文档路径,便于追溯

## 7. 失败处理

| 场景 | 处理 |
|------|------|
| 子模式 1A: 用户提供的文档路径不存在 | 报错,提示用户检查路径;或询问用户是否粘贴文档内容 |
| 子模式 1A: 关联文档获取失败(change 目录下缺失某些文档) | 跳过缺失文档,使用已获取的文档继续;在"文档来源"中注明缺失 |
| 子模式 1B: 未发现任何 apply 完成的 change | 报错,提示用户"未发现已完成 apply 环节的 openspec change,请确认 change 状态或改用子模式 1A 直接提供文档" |
| 子模式 1B: change 文档读取失败(目录缺失 proposal/design 等) | 跳过缺失文档,使用已获取的文档继续;在"文档来源"中注明缺失;若核心文档(design/proposal)均缺失则报错 |
| 子模式 1B: tasks.md 无法判定 apply 完成度 | 将该 change 排除出候选列表;若所有 change 均无法判定,提示用户改用子模式 1A |
| 文档内容无法解析(格式异常) | 报错并输出原始文本片段,提示修正格式 |
| 文档中无显式功能点(纯背景介绍) | 报错,提示用户提供的文档需包含 design/proposal/tasks 等具功能描述的文档 |
| 预探索失败(URL 不可访问 / MCP 不可用 / snapshot 为空) | 降级为无探索模式,用例中保留 `<>` 占位符,并在 `.md` 顶部标注 `> ⚠️ 预探索失败: <原因>,用例中 UI 元素名使用占位符,待页面可访问后补全` |
| 用户未提供 URL 且拒绝提供 | 降级为无探索模式,标注 `> ⚠️ 未提供目标 URL,未进行浏览器预探索,用例中 UI 元素名使用占位符` |
