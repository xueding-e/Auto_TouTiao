# AI 验证基准语法契约

> 本文档为 `test-case-generator` skill 的横切规则,定义 AI 验证基准的检查项结构、判定规则、语义匹配规范,以及 `.md` 文本格式与 `.page-structure.yaml` 结构化格式之间的等价映射。三种输入模式(文档 / URL / 已有用例)共用本规范,各模式的"场景→基准映射表"见对应 mode 文件。主文件: [SKILL.md](../SKILL.md)

---

## 一、检查项结构

每条 AI验证基准由多个检查项组成,用 `;` 分隔。检查项分为两类:

| 标记 | 类型 | 示例 | 不满足时的后果 |
|------|------|------|-------------|
| 无前缀或 `①`~`⑨` | **核心条件**(必须满足) | `①snapshot中不再出现"新增"对话框` | 导致 FAIL |
| `可能出现` 前缀 | **弱条件**(最好满足) | `④可能出现含"成功"的提示信息` | 不影响结果 |

> `;` 用于分隔层级最高的独立检查项。同一检查项内部的多个选项使用 `/` 分隔(如 `含"A"/"B"`)。生成侧编写时确保 `;` 只出现在独立检查项之间,不在单个检查项内部使用。

---

## 二、检查项类型与判定规则

| 检查项类型 | 示例 | AI 判定逻辑 |
|-----------|------|------------|
| **反向断言**: `snapshot中不再出现"X"` | `snapshot中不再出现"新增知识库"对话框` | snapshot 全文搜索不到 `"X"` → 通过; 搜索到 → 不通过 |
| **正向断言**: `snapshot中出现含"X"的Y` | `表格中出现含"测试知识库"的新增行` | snapshot 中存在同时满足"X"和 Y 特征的区域 → 通过; 缺失 → 不通过 |
| **多选匹配**: `含"A"/"B"/"C"` | `含"必填"/"不能为空"/"请输入"的校验提示` | snapshot 中出现 A、B、C **任意一个** → 通过; 全未出现 → 不通过 |
| **量化对比**: `N值比操作前<增加/减少>K` | `"共N条"中N值比操作前增加1` | 对比操作前后 snapshot,数字变化量 = K → 通过; 否则 → 不通过 |
| **一致性断言**: `与操作前一致` | `表格行数与操作前一致(未增加)` | 操作前后数据相同 → 通过; 变化 → 不通过 |
| **页面健康检查**: `页面不出现error` | `页面不出现error/异常提示` | snapshot 中无 "error"/"异常"/"失败"/"500"/"404" → 通过 |
| **URL 断言**: `URL包含<关键词>` | `URL包含kbUpload` | snapshot 输出中 url 字段包含关键词 → 通过 |

## 三、语义匹配规则

> AI 做语义判断,非关键字精确匹配。生成基准时使用 `含"A"/"B"` 格式给出多个等价表述,提高 AI 判定通过率。

| 业务断言 | AI验证基准中的等价表述(任一匹配即通过) |
|---------|--------------------------------------|
| 名称必填 | `含"必填"/"不能为空"/"请输入"的校验提示` |
| 创建/保存成功 | `含"成功"/"创建成功"/"保存成功"/"操作成功"的提示信息` |
| 删除成功 | `含"成功"/"删除成功"/"移除成功"的提示信息` |
| 对话框关闭 | `snapshot中不再出现"<对话框标题>"对话框` |
| 列表刷新 | `表格/列表可见行变化;底部"共N条"中N值变化` |
| 页面加载完成 | `snapshot中存在<关键元素>;页面不出现"加载中"/"loading"/error提示` |

## 四、与预期结果的互补关系

| 维度 | 预期结果(面向人) | AI验证基准(面向 AI) |
|------|------------------|---------------------|
| 语言风格 | 业务语言,可读性强 | snapshot 可观测语言,精确可验证 |
| 粒度 | 粗粒度,概括性描述 | 细粒度,逐条可检查 |
| 示例 | `提示"名称必填";未创建成功` | `【步骤4后】①snapshot中仍存在"新建"对话框(未关闭);②对话框内出现含"必填"/"不能为空"的校验提示;③表格行数与操作前一致(未增加)` |

## 五、生成侧编写规范(三模式共用)

1. 每条基准以 `【步骤N后】` 前缀标注触发步骤,N 对应 `.md`"点击步骤"列的步骤序号
2. 多个验证点用 `;` 分隔,推荐用 `①②③④` 编号区分核心条件与弱条件
3. 成功类场景必须包含 **正向断言**(出现什么) + **反向断言**(不出现什么) + **量化变化**(数量增减)
4. 校验类场景使用 `含"A"/"B"` 格式给出多个近义校验词,提高语义匹配通过率
5. 跳转类场景必须描述 URL 变化(包含真实路径关键词)和 **至少2个** 目标页面特征元素
6. 列表展示场景必须列出探索时观察到的 **真实表头字段名**(至少4个),不用模糊描述
7. 预探索成功后,所有 `<>` 占位符必须替换为预探索获取的真实元素名;若预探索降级则保留 `<>` 占位符并标注"待页面探索确认"
8. 各模式的"场景→基准映射表"见对应 mode 文件:
   - 模式一: [mode1-document.md](./mode1-document.md) 第 4 节
   - 模式二: [mode2-url.md](./mode2-url.md) 第 5 节
   - 模式三: [mode3-convert.md](./mode3-convert.md) 第 5 节

## 六、.md 文本格式 ↔ yaml 结构化格式映射

> `.md` 表格"AI验证基准"列与 `.page-structure.yaml` 的 `cases[<id>].ai_verification_benchmarks` 字段必须等价。生成侧按以下规则转换,字段定义详见 [page-structure-yaml-spec.md](./page-structure-yaml-spec.md)。

| .md 文本格式 | yaml 结构化格式 |
|--------------|----------------|
| `【步骤5后】` | `step_ref: 5` |
| `①snapshot中不再出现"X"` | `{type: core, assertion: not_appear, target: "X", options: [], compare: null}` |
| `①snapshot中出现含"X"的Y` | `{type: core, assertion: appear, target: "X", options: [], compare: null}`(Y 的特征合入 target 描述) |
| `含"A"/"B"/"C"` | `{type: core, assertion: match_any, target: "A", options: ["A","B","C"], compare: null}` |
| `N值比操作前增加K` | `{type: core, assertion: quant_compare, target: null, options: [], compare: "增加K"}` |
| `与操作前一致` | `{type: core, assertion: consistent, target: null, options: [], compare: "与操作前一致"}` |
| `页面不出现error` | `{type: core, assertion: no_error, target: null, options: [], compare: null}` |
| `URL包含<关键词>` | `{type: core, assertion: url_contains, target: "<关键词>", options: [], compare: null}` |
| `④可能出现含"成功"的提示` | `{type: weak, assertion: match_any, target: "成功", options: ["成功","创建成功","保存成功","操作成功"], compare: null}` |

**生成侧硬性要求**:
1. 每个 `case` 的 `ai_verification_benchmarks` 必须与 `.md` 表格中该用例的"AI验证基准"列**逐项等价**,不得遗漏或新增
2. `step_ref` 必须与 `steps[].seq` 对应,确保 runner 知道每个检查项在哪个步骤后执行
3. `core`/`weak` 标记必须与 `.md` 中的 `①`~`⑨`(无 `可能出现` 前缀) vs `可能出现` 前缀一致
